# prajwal-prathiksh.github.io

Source for my personal site, <https://prajwal-prathiksh.github.io>. It is built with [Astro](https://astro.build) as plain static HTML and CSS, with a little TypeScript for the games. GitHub Actions builds and deploys it to GitHub Pages.

## Local workflow

Needs Node 22.12 or newer.

```sh
npm install        # once, or after pulling dependency updates
npm run dev        # live-reloading preview at http://localhost:4321
```

Before pushing, check that the production build works and looks right:

```sh
npm run check      # type and template errors
npm run build      # writes the static site to dist/
npm run preview    # serves dist/ at http://localhost:4321
```

Push to `main` and the [Deploy workflow](.github/workflows/deploy.yml) builds and publishes the site in about a minute. Pull requests run the same build without deploying.

## Adding a game

1. Create `src/pages/playroom/<name>.astro`, using `tic-tac-toe.astro` as a template. Game logic goes in a `<script>` tag and runs only in the browser.
2. Add an entry to `src/data/games.ts`.
3. Save high scores with `loadScores` and `saveScores` from `src/scripts/scores.ts`.

Scores stay in the visitor's `localStorage` under keys prefixed `pp-games:`. They never leave the device, and the site uses no cookies or analytics. `/playroom/` has a button that clears them. The optional Chowka Bhara online lobby uses a small signaling relay; see below.

### Training Chowka Bhara

The game has two boards: the classic 5×5 with four pawns and four cowries each (throws 1–3, chowka 4, bhara 8), and the 7×7 with six pawns, six cowries (throws 1–5, chowka 6, bhara 12) and three rings. On the 7×7 board a pawn steps diagonally from the outer ring onto the middle ring's crossed corner, and both inner rings run clockwise. Chowka and bhara earn another throw on either board; there is no limit on how many in a row. One geometry module (`boardFor` in `src/scripts/chowkaBhara.ts`) defines each board's paths, rings, safe squares, pawn count and cowrie throws. The rules, bots, models, page, online lobby, thumbnail and training tools all read it, so neither board has separate code. Hand-tuned heuristics measure progress on the 5×5 scale (`classicSteps`), and model features are divided by pawn count and path length, so the same weights work on both boards.

Chowka Bhara's Hard opponent combines bounded lookahead with a compact evaluator trained by self-play. It scores the board and the current turn, including held throws, capture and finishing options, owed throws, bonus streak risk, and likely follow-up captures. During a match, each player also maintains a small probability distribution over every opponent's playing style. Observed move choices update that profile, and reply search uses the inferred mixture instead of assuming balanced play. Trust, grudges, refusals, and betrayals remain separate relationship-specific memories.

The simulator imports the same TypeScript rules as the browser game. Training and model comparisons use four players with every pawn starting at home. Worker threads run the training locally without Python or a GPU.

```sh
npm run selfplay:smoke
npm run selfplay:benchmark -- --budget=96 --repeats=20
npm run selfplay:train -- --generations=3 --population=6 --games=96
npm run selfplay:tournament -- --games=160
npm run selfplay:baseline -- --games=180
npm run winmodel:train -- --games=1500 --validation-games=300 --test-games=300 --epochs=40
```

Every command takes `--board=5` (the default) or `--board=7`. The smoke test checks both boards either way.

Evaluator training writes weights to `src/data/chowka-bhara-model.json`, or `src/data/chowka-bhara-model-7x7.json` for the 7×7 board. Both 7×7 files are copies of the 5×5 weights marked `"borrowedFrom": 5` and stay that way until 7×7 training runs. Until then, the page says its 7×7 win outlook is only a rough guide. Runs are reproducible with `--seed=<number>`, and `--workers` and `--budget` control runtime. Candidate evaluators must beat the incumbent in separate holdout games before their weights replace it. A positive tournament budget compares evaluators inside live-style search; zero uses the faster one-ply self-play policy. The baseline command compares against the frozen Hard AI from commit `a71e7b8`.

The win outlook appears in games with two to four players. After someone finishes, it switches to the next open place and removes finished players from the probability bar. Its separate softmax model in `src/data/chowka-bhara-win-model.json` (or `-7x7.json`) trains only on four-player, home-start games, so other setups have no measured calibration. Training samples decisions for first, second, and third place, including positions after rolls, and excludes places that were not actually finished. Features cover held values, remaining throws, streak risk, finishing options, and which opponent a held roll can capture. Separate game sets fit the weights, select the probability temperature, and measure log loss, Brier score, accuracy, and calibration by place and roll phase.

The page samples the outlook at every board-history step. When the first place is decided, a race replay charts how each player's chances moved, one band per place, with the lead changes and the biggest single swing. It opens again when a watched game finishes, and the Race replay button reopens it. To check it without playing a whole match, open `/playroom/chowka-bhara/?debug` and choose an ending under Testing. The page plays a quick headless game with Easy computers (`src/scripts/chowkaBharaEndgame.ts`), keeps its real history and outlook, and resumes one finishing move before you take 1st, 2nd or 3rd, or before a computer's move leaves you last. These test games are not added to the saved record.

A game built with another tool (plain JS, a canvas engine, WebAssembly) can also go in `public/playroom/<name>/` as static files. Astro copies that folder into the site unchanged.

GitHub Pages only serves static files. Anything that runs in the browser works. Server code, databases, and online leaderboards do not. The limits are 1 GB per site and 100 MB per file.

### Chowka Bhara with friends

`/playroom/chowka-bhara/online/` offers two ways to play on separate phones, and the game page links to both. In each, the host's browser runs the rules, cowrie throws, bots and social play; guests send commands for their own seat, and the host checks each one and sends snapshots after rolls and moves. Each person sees their own home square at the bottom, with the win outlook and board history. While a player is away the match pauses; the host can wait, continue with a bot in that seat, or restart with a bot. The session layer (`src/scripts/chowkaOnlineLobby.ts`) does not care how messages travel: an online link and a nearby link report the same events.

**Online.** The host creates a room with a six-character code (no 0/O or 1/I/L) and shares it with the Share button, a link, or a QR code. Up to three friends ask to join and the host lets them in. Every message travels over one WebSocket per phone to the Cloudflare Worker in `worker/chowka-signal.ts`, one Durable Object per room, so there are no direct connections to fail on mobile networks. Phones drop connections when they switch apps, so a drop never means leaving. Every player, the host included, keeps a private seat key in local storage, and reconnecting with it returns the same seat. `src/scripts/chowkaRelay.ts` reconnects with back-off, again at once when the page becomes visible or the network returns, and pings every 15 seconds; the Worker treats a socket silent for 45 seconds as dropped. A room waits 30 minutes for an absent host and queues join requests meanwhile. The host also saves the room and the latest game snapshot on the device, so a host tab that iOS reloads in the background resumes the same match. The Worker keeps only the room's seats and keys, deletes them when the room ends, and stores no game state.

**Nearby.** Phones on the same Wi-Fi or hotspot connect directly over WebRTC data channels with no internet. `src/scripts/chowkaNearby.ts` swaps the one-time connection offer and answer as QR codes: the host shows an invite link, a guest scans it with the phone's Camera, and the host scans the guest's reply in the page (`src/scripts/chowkaQr.ts`; jsQR where the browser has no BarcodeDetector, as in Safari). Each code reduces the connection description to its ICE credentials, DTLS fingerprint, role and addresses, about 180 characters, and the receiver rebuilds a standard description. No ICE servers are used. The service worker keeps the pages on the device, so everyone needs to have opened the site once while online. A player who drops scans a fresh code; a phone the host does not recognise takes over an away seat.

To test locally:

```sh
npm run build
npm run preview -- --host 127.0.0.1 --port 4324
# In another terminal:
npm run signal:dev
```

Open `http://127.0.0.1:4324/playroom/chowka-bhara/online/` and create a room. Open the invite link in a private window, enter a different name, and join. Let them in from the host tab, then start the game. Both should show the same throws, moves and history. Refresh either tab: it should rejoin the running match. For Nearby, use "Host a nearby game", open the "Copy the link" invite in a private window, and paste its reply code back. Phones need HTTPS for the camera and share sheet, so test them through an HTTPS tunnel to the preview and relay.

For public rooms, deploy `wrangler.jsonc` to a Cloudflare account and set the GitHub repository variable `PUBLIC_CHOWKA_SIGNAL_URL` to its `wss://` address. The deploy workflow passes that variable into the static build. Until the Worker is deployed and the variable is set, the public page explains that online rooms are unavailable; Nearby still works. The Worker allows WebSocket connections only from `https://prajwal-prathiksh.github.io`; change `SITE_ORIGIN` if the site moves. Room codes travel in URL fragments, which are not sent in ordinary HTTP requests, though the relay sees the code in its WebSocket path. Players in a nearby game can see one another's local network addresses.

## Tools

`/tools/gift-exchange/` makes a random gift exchange draw from a list of names and optional mutual exclusions. The organizer can set an event name for the copied messages. It finds a complete valid assignment or explains that the exclusions make one impossible. The organizer sees all pairings and can copy an individual message for each participant. Names, exclusions, and results stay in the current browser tab and disappear on refresh; the tool uses no account, room link, or backend for the draw.

## Offline and installing

The site is a Progressive Web App. `npm run build` runs `astro build`, then `scripts/build-sw.mjs`, which uses Workbox to write `dist/sw.js`. That service worker saves the pages, scripts and images on the device, so the site and all the games work offline after one visit. The CV and resume PDFs aren't saved; they open from the network as usual. People can install it: "Install app" in Chrome or Edge, or Share → Add to Home Screen on iPhone and iPad. When a new version is deployed, open pages show a "A new version is ready" notice with a Refresh button.

The app details live in `public/manifest.webmanifest`. The icons are drawn in `scripts/icons/*.svg`; after changing them, run `sh scripts/make-icons.sh` (needs `rsvg-convert`) to redraw `public/icons/`.

The service worker only runs in the built site. To try it locally, use `npm run build && npm run preview`, not `npm run dev`.
